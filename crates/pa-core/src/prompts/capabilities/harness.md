# harness: persistent memories, notes, skill entries, subagent specs, and refinement

The continual harness store outlives the turn and compaction. Entries go to this session's store unless `#:global #t` selects the cross-session one; a name written `global:<name>` or `local:<name>`, as the overview shows it, is accepted as is. An unsaved session has no local store: pass `#:global #t`. An entry is `{id, kind, title, content, path, scope, reference, arguments, metadata, source, created_at, updated_at, version}`: `kind` is `"prompt"`, `"memory"`, `"skill"`, `"subagent"`, or `"factory"`; `scope` is `"local"` or `"global"`; `source` is `"agent"` or `"refine"`; `version` starts at 1 and grows with every update. `id` is the entry's name. Everything raises while the user has harness refinements turned off in `/settings`.

- `(harness-put kind name content #:title #:path #:reference #:arguments #:dag #:machine #:metadata #:global)`: create the entry `name` of `kind`, or update it when it is stored (an upsert); the entry. A new entry is titled `name` unless `#:title` says otherwise and is filed under `#:path` (`"policy"` for a prompt note, standing guidance; `"general"` otherwise); an update keeps every field it omits and bumps `version`
  - `"skill"`: describes a Scheme function of an installed skill. Its first write needs `#:reference`, a hash with `'type "scheme"`, `'skill` (the installed skill whose `skill.scm` or `scheme/*.scm` defines the function), and a `'callable` (the function's name) or `'call_pattern` (a call of it); `#:arguments` describes its parameters
  - `"subagent"`: a reusable brief for `rlm-spawn`
  - `"factory"`: a state machine `factory-run` runs by its name. The spec is `#:machine` or `#:dag`, exactly one, validated first: an invalid spec is never stored, a first write needs one, and an update without one keeps the stored spec. Refused while the factory is disabled
- `(harness-delete kind name #:global)`: delete one entry; whether it existed. A factory entry may be deleted while the factory is disabled
- `(harness-query [query] #:view #:kind #:limit #:state-dir #:global)`: read one store. With `query`, entries ranked by how well they match its words, best first, at most `#:limit` (default 10); `#:kind` narrows to one kind. Without it, `#:view` picks what comes back: `"overview"` (the default: a readable summary as a string: the store's file, each kind's count and first `#:limit` entries, default 20, and the last refinements), `"state"` (the store in full: `{scope, file_path, entries, refinements}`, `entries` keyed by kind and then id; `#:state-dir` reads another agent's store from its harness directory), or `"reuse"` (see below)

A stored entry earns its place by being reused: every installed skill is listed in every session's prompt, and every global entry a digest shows costs its line there, so an entry used only in the session that made it costs more than it saves. The ledger counts, per entry, the sessions other than its creator's that were offered and used it: a skill is used when its `SKILL.md` is read with `fs-read`, a `/skill:` command expands it, or a cell names a function its Scheme source defines; a global harness entry is used when a `harness-query` search returns it. Local entries are not counted.

The reuse view, `(harness-query #:view "reuse")`, is one hash per installed skill and global harness entry: `key`, `store` (`"skill"` or `"harness"`), `kind`, `name`, `standing` (`"reused"`: used in two or more later sessions; `"used-once"`; `"unused"`: offered to three or more, used by none; `"new"`: too few to tell), `created-at`, `creator-known`, `created-here`, `offered-sessions`, `used-sessions`, `uses` (in later sessions), `own-uses`, `last-used-at`, `prompt-bytes`, `prompt-tokens`, `removable`. Answered while harness refinements are off. Nothing is removed automatically: suggest that the user prune dead weight with `prime-agent reuse prune <key>`, or update the entry so later sessions find it

Refinement has another model read the transcript and apply small, evidence-backed edits to the store (the user's `/refine`). It never runs mid-cell: a scheduled refinement runs when the turn ends, the harness rebuilds the system prompt, sends a message with the result, and resumes you.

- `(refine-run [instructions] #:global #:plan-only)`: schedule a refinement for when the turn ends: `{scheduled #t}`, or `{scheduled #f, reason}`. `instructions` focus it on one observation; `#:global #t` targets the cross-session store. Calling it again before the turn ends only updates the instructions. With `#:plan-only #t` nothing is scheduled: it returns a suggested diagnose, update, validate plan for the observation `instructions`, as a list of steps
- `(refine-record trigger changes #:evidence #:outcome #:id #:global)`: record one refinement pass in the store: `{id, trigger, changes, evidence, outcome, created_at}`. `trigger` says what caused it; `changes` is one string or a list of them
- `(refine-status)`: `{pending, in_flight}`: whether a refinement is queued for this turn, and whether one is planning or applying
