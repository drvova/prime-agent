# shell: commands and their jobs

Each command is its own shell in the session's working directory: shell state (`cd`, variables) does not carry over to the next call, so chain with `&&` inside one command. A job argument is a job id or any hash these functions return.

- `(bash command [options])`: run `command` and wait for it. The result is `{running #f, exit-code, output, truncated, timed-out, duration-ms, cached, job, pid, handle, tests}`: `output` is stdout and stderr together in the order written; `handle` is the `out:<id>` handle of a large output (page it with the `ctx-*` functions) or `#f`; `tests` is the parsed summary of a test run (cargo test, pytest, unittest, go test, jest, vitest: counts and each failure, also printed) or `#f`; `cached` marks a repeated read-only command (`git status`/`log`/`diff`, `ls`, `cat`, `rg`, `grep`) answered from its last result because its inputs did not change. A failing command is a result with a non-zero `exit-code`, never an error
  - The wait has a window: 10 seconds in a session that delivers `[bash-done]` notices, at most 600. A command that outlives it keeps running in the background and the call returns a snapshot instead: `{running #t, exit-code #f, output, output-truncated, duration-ms, job, pid, queued, command, note}` with `output` its newest 20 lines. Its result arrives with the `[bash-done]` notice, or through `bash-wait`
  - Options: `'wait-ms` (this call's window; `#f` for none), `'timeout-ms` (kill the command after this long and wait for it until then; `timed-out` is then `#t`), `'background #t` (do not wait: returns the job `{job, pid, command, running, queued, persistent}`), `'persistent #t` (POSIX, saved sessions only: a shell that survives kernel, worker, and daemon restarts and ends only on its own exit or an explicit kill; only for a server or long job that must outlive a restart), `'elevated #t` (run with administrator or root rights once the user approves the system's prompt; see Administrator and root rights below)
  - In a session that delivers `[bash-done]` notices, a `[bash-quiet]` notice arrives when every background job still running has written nothing for 3 minutes while the session is idle: each job's id, pid, run and quiet time, command and newest output. It comes again after 12 and then 48 minutes of silence, never more than three times for one job, and new output starts the count again. A quiet job may be stuck (waiting for input, a lock, the network): look at it with `(bash-output job #:tail 20)` and end it with `bash-kill`, or end the turn again if it is only slow
  - A command the call waits for is killed when its cell is stopped or times out. A background job, a snapshot's job, and a persistent shell outlive their cell. Over the session's job limit a background command is held `queued` until a slot frees
- `(bash-wait job [seconds])`: wait for a job, for `seconds` or the session's window; its result, or a snapshot when it is still running
- `(bash-output job #:tail)`: where the job stands and everything it has written so far, or its last `#:tail` lines: a finished job's result, or while it runs `{job, pid, command, running, queued, persistent, exit-code #f, output}`. `running` is whether anything of the job still runs; `output` is the text written so far, which never waits
- `(bash-kill job [options])`: signal the job's whole process group; whether it was still running. Options: `'signal` (`'term`, the default, or `'kill`), `'grace-ms` (how long after a `'term` the group is killed; default 5000)
- `(bash-jobs #:persistent)`: the kernel's jobs, each `{job, pid, command, status, exit-code, duration-ms, started-at, persistent}`. With `#:persistent #t` the session's persistent shells instead, re-attached ones included, as `{job, pid, command, running, queued, persistent}`; after a restart this is how to get their jobs back

## What `bash` is

Commands run on a bash-compatible shell built into Prime Agent, on every platform, and `$PRIME_AGENT_SHELL` is `builtin`. Bash's language works as written: pipelines, redirections, `&&` and `||`, loops, functions, arrays, `[[ ]]`, `$(...)`, `<(...)`, here-documents, `set -euo pipefail`. Only when the user's settings ask for it (`"shell": "system"`, or a `shellPath`) do commands run on the machine's own shell program, and then nothing below applies.

- Built in, with no program started: the shell's builtins (`cd`, `echo`, `printf`, `test`, `read`, `export`, ...) and `basename cat chmod cp cut date dirname env find grep head jq ls mkdir mv printenv realpath rm rmdir sed seq sleep sort tac tail tee touch tr uname uniq wc which whoami xargs yes`, each with the common GNU options. An option one of them lacks is handed to the program of that name when the machine has one; with none the command fails with `... is not supported by Prime Agent's built-in <name>, and no <name> program is installed on this machine`: then use another option, the `fs-*` functions, or Scheme
- Anything else (`git`, `cargo`, `python`, `awk`, `curl`, ...) is a program found on `PATH` and started directly. A path runs the program even where the name is built in (`/bin/sleep 5`). On Windows, paths are Windows paths and Unix directories such as `/tmp` do not exist (`> /dev/null` works)
- `pid` in a result is a job number, not a process id, and `$$` is that number: it names no process to signal or watch. `$!` is the process id of a background program (`server & pid=$!`, then `kill $pid` or `wait $pid`), and empty for a background loop, group, function, or built-in command (`sleep 5 &`)
- No signal reaches a script. `trap` handlers run for `EXIT`, `ERR`, `DEBUG` and `RETURN` only, and a command that is killed, stopped or timed out runs no `EXIT` handler: clean up in a later command. `umask`, `ulimit` and `suspend` are refused, and `exec cmd` runs `cmd` and ends the script
- Without the program of the same name: `grep` and `sed` patterns take no back-references (`\1` in the pattern), `sed` has no branches (`b`, `t`), `find` has no `-exec` (pipe to `xargs`), and names and `sort` order by bytes. `sed -i` replaces its file whole, as GNU sed does (other hard links keep the old text), keeping its mode, but a symlink keeps pointing at the edited file instead of becoming a regular file
- A command may expand at most 1,000,000 brace words (`{1..N}`), 32 MiB in one word or variable, and 32 MiB of `$(...)` output; past that it fails with a message and the line it is on ends
- `jq` takes jq 1.7's options and prints as jq does, on the `jaq` interpreter. Where they differ: regular expressions take no look-around and no back-references, integers stay exact past 2^53, and JSON nested deeper than 10,000 levels is refused. A filter that defines a recursive function, or uses `--stream`, `input_line_number`, `$__loc__`, `localtime` or modules, runs on the `jq` program and needs it installed

## Administrator and root rights

Commands run on the user's own computer, not in a sandbox or container, with the rights of the user's account unless the session is elevated: the environment section of the prompt says which (Administrator on Windows, root on Linux and macOS). A step that needs those rights runs with `(bash command (hash 'elevated #t))`; in an elevated session every command already has them, with no consent step, and the option changes nothing.

- The system asks the user first, on their screen: Windows its UAC prompt, Linux and macOS a password dialog (`sudo`'s askpass program, the desktop's polkit agent, or the macOS dialog) that names the command. The password never passes through you or the transcript. Say why the step needs the rights before you run it. The call waits while the user answers, as for any command: past the wait's window it returns a snapshot with `running` `#t`, and `bash-wait` waits on
- The result is a command's result: `exit-code`, `output` (stdout and stderr together), `duration-ms`, `job`; the job functions (`bash-wait`, `bash-output`, `bash-kill`, ...) work on it, with `'background`, `'wait-ms` and `'timeout-ms` too. Killing the job, or stopping its cell, ends the command and everything it started. `'elevated` cannot be combined with `'persistent`
- A declined prompt, or a machine where no prompt can be shown (a login over SSH with no desktop, no askpass program or polkit agent, `sudo` needing a password), is a result with `exit-code` 126 and an `output` that starts `elevation declined:` or `elevation unavailable:`: the command did not run. Do not try a declined one again without asking the user
- Windows: one approval starts an elevated helper for the session, which runs its elevated commands without asking again until the session ends or none has run for 10 minutes; the next one then asks again. They run on the built-in shell (or the session's shell program) in the session's working directory and environment
- Linux and macOS: each elevated command asks (unless `sudo` still remembers the sign-in) and runs as root on the system's `bash`, not the built-in shell, with the environment `sudo` or `pkexec` gives root (its own `PATH` and `HOME`). Files it creates belong to root: give them back with an elevated `chown` when they are the user's
- Fallback, when the option cannot help: give the user the exact command and `ask` them to run it in a terminal of their own (opened with "Run as administrator" on Windows, with `sudo` elsewhere)
